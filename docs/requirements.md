# AWS Step Functions 検証 — 要件定義書

- 作成日: 2026-09-06
- 対象: 検証用 AWS アカウント / リージョン `ap-northeast-1`
- リポジトリ: https://github.com/DarthMazz/step-function-eval

---

## 1. 背景と目的

SQS を起点とした非同期処理パイプラインを AWS Step Functions で組んだ場合に、
**「並列処理のうち一部だけを早く返す」品質目標が達成できるか**を実機で検証する。

業務ロジックそのものの実装は目的ではない。**フローの成立性と時間特性の実測**のみを対象とする。

## 2. 検証対象フロー

```
[送信元] → SQS → ① 受付Lambda → StartExecution
                                    │
        ┌───────────────────────────┴──────────────────────────┐
        │  Step Functions State Machine (Standard)             │
        │                                                       │
        │   ② 前処理                                            │
        │        ↓                                              │
        │   ③ Parallel（4分岐・同一入力を別々に加工）            │
        │      ├─ 加工A ─→ 結果書き出し   ← 最短で返す（10秒以内）│
        │      ├─ 加工B ─→ 結果書き出し   ← 15秒以内             │
        │      ├─ 加工C ─→ 結果書き出し   ← 15秒以内             │
        │      └─ 加工D ─→ 結果書き出し   ← 15秒以内             │
        │        ↓                                              │
        │   ④ 全体完了マーク                                     │
        └───────────────────────────────────────────────────────┘
                                    │
                              DynamoDB（結果ストア）
                                    ↑
                        呼び出し元がポーリングで取得
```

## 3. スコープ

### 対象
- ①②③④ の各処理の**スタブ実装**（指定秒数スリープして固定値を返すだけ）
- SQS → Lambda → Step Functions の起動連携
- Parallel による4並列実行
- 各ブランチからの個別結果書き出し（DynamoDB）
- 到達時刻の実測と品質目標の達成判定

### 対象外
- 実際のデータ加工ロジック
- 認証・認可、マルチテナント、暗号化要件
- 本番運用を想定した監視・アラート設計
- コスト最適化

## 4. 機能要件

| ID | 要件 |
|---|---|
| FR-1 | SQS キューにメッセージを1件投入すると、受付 Lambda が起動する |
| FR-2 | 受付 Lambda はステートマシンを**非同期**で起動する（結果を待たない）。起動後ただちに SQS メッセージを削除する |
| FR-3 | 受付 Lambda は SQS の `SentTimestamp`（メッセージ到着時刻）をステートマシンの入力に引き渡す |
| FR-4 | 同一メッセージが再配信された場合、実行が二重に開始されない（`messageId` を実行名に用いた冪等化） |
| FR-5 | ステートマシンは ② 前処理を実行し、その出力を ③ の4分岐すべてに同一入力として渡す |
| FR-6 | ③ は Parallel ステートで4つの加工を**同時に**開始する |
| FR-7 | 各分岐は、自分の加工が終わった時点で**他の分岐の完了を待たずに** DynamoDB へ結果を書き込む |
| FR-8 | 各書き込みレコードには、SQS 到着時刻・書き込み時刻・経過ミリ秒を含める |
| FR-9 | 4分岐すべての完了後、④ で全体完了レコードを DynamoDB に書き込み、実行を正常終了する |
| FR-10 | 各処理のスリープ秒数は環境変数／テンプレートパラメータで変更できる |

## 5. 非機能要件（品質目標）

| ID | 要件 | 計測起点 | 目標 |
|---|---|---|---|
| NFR-1 | 加工A の結果が DynamoDB から読める | **SQS へのメッセージ到着時刻** | **10秒以内** |
| NFR-2 | 加工B / C / D の結果が DynamoDB から読める | 同上 | **15秒以内** |
| NFR-3 | 加工A の結果到達は、加工B/C/D の完了に依存しない | — | B/C/D が遅延しても A は NFR-1 を満たす |

計測起点は SQS 到着時刻とするため、以下のオーバーヘッドがすべて予算に含まれる:
SQS のポーリング間隔 / Lambda のコールドスタート / `StartExecution` の反映 / 各ステート遷移。

## 6. 設計方針と根拠

### 6.1 なぜ「各分岐が自分で書き出す」のか（最重要）

Step Functions の **Parallel ステートは全ブランチの完了を待ってから次に進む**。
ステートマシンの出力経路に結果を載せると、加工A の結果も最も遅い分岐（B/C/D）に引きずられ、
NFR-1（10秒以内）は原理的に達成できない。

したがって、**各分岐の末尾に DynamoDB への書き込みステートを置き、副作用として結果を外部に出す**。
Parallel の完了は「全部終わった」ことを示すだけの意味になる。

### 6.2 なぜ Map ではなく Parallel か

4つの加工は**それぞれ中身の異なる処理**であるため、同一ロジックの繰り返しを表す `Map` ではなく、
分岐を明示的に列挙する `Parallel` が適切。
（将来「同時実行数を絞りたい」要件が出た場合は `Map` + `MaxConcurrency` への変更を検討する。`Parallel` に同時実行数の制御機能は無い。）

### 6.3 なぜ Standard か

- 実行履歴が全件・構造化されて残るため、各ステートの開始/終了時刻を `GetExecutionHistory` だけで実測できる
- 想定実行時間は最大15秒程度で、Standard のオーバーヘッド（数百ms）は許容範囲
- Express は履歴が CloudWatch Logs 依存になり、時刻の突き合わせが煩雑

### 6.4 DynamoDB 書き込みは Lambda ではなく SDK 統合

書き込みを Step Functions の AWS SDK 統合（`aws-sdk:dynamodb:putItem`）で行う。

- Lambda を1つ減らせる
- **書き込み完了時刻が実行履歴にステートとして残る**ため、到達時刻の実測がそのまま取れる
- 加工 Lambda を差し替えても書き込み仕様が変わらない

### 6.5 クエリ言語は JSONata

経過ミリ秒の算出（`$millis() - enqueuedAt`）に算術が必要で、JSONPath の組み込み関数では実現できない。
JSONata（`QueryLanguage: JSONata`）を採用する。入出力処理の検証という当初目的にも合致する。

### 6.6 Lambda コードはテンプレートにインライン記述

スタブは数十行のため、CloudFormation の `Code.ZipFile`（Python 3.12）でインライン定義する。
S3 アーティファクトバケットもビルド手順も不要になり、`aws cloudformation deploy` 一発で完結する。

### 6.7 加工A〜D は単一の汎用スタブ Lambda を共用

4分岐は ASL 上は独立した Task ステートだが、呼び出す Lambda は共通の汎用スタブ1つとし、
`stage` と `sleepSeconds` をペイロードで渡し分ける。フロー検証には十分で、後から個別関数へ分割するのも容易。

## 7. リソース一覧

命名プレフィクス `sfeval-` / CloudFormation スタック名 `sfeval-poc`。

| 種別 | 論理名 | 備考 |
|---|---|---|
| SQS | `sfeval-intake` | 標準キュー。`VisibilityTimeout` は受付 Lambda タイムアウトの6倍 |
| SQS | `sfeval-intake-dlq` | `maxReceiveCount: 3` |
| Lambda | `sfeval-intake` | SQS イベントソースマッピング（`BatchSize: 1`）→ `StartExecution` |
| Lambda | `sfeval-worker` | 汎用スタブ。`sleepSeconds` 秒スリープして固定値を返す |
| Step Functions | `sfeval-workflow` | Standard / JSONata / ログ ALL + 実行データ含む |
| DynamoDB | `sfeval-results` | PK `executionId` (S) / SK `taskName` (S) / オンデマンド / TTL `expireAt` |
| CloudWatch Logs | `/aws/vendedlogs/states/sfeval-workflow` | 保持期間 7日 |
| IAM Role | 受付 Lambda 用 / worker 用 / ステートマシン用 | 最小権限で個別に定義 |

### スタブのスリープ秒数（初期値・パラメータ化）

| 処理 | 秒数 | 想定到達（SQS到着から） |
|---|---|---|
| ② 前処理 | 1 | — |
| ③ 加工A | 1 | 約 2〜4秒（目標 10秒） |
| ③ 加工B / C / D | 8 | 約 9〜11秒（目標 15秒） |

加工A と B/C/D に明確な差をつけることで、**A が B/C/D を待っていない**ことを実測で示す。

## 8. 受け入れ基準

| ID | 判定内容 | 判定方法 |
|---|---|---|
| AC-1 | SQS 1件投入で SFN 実行が1件だけ開始される | `ListExecutions` |
| AC-2 | ② 前処理が ③ より先に完了している | 実行履歴のステート順序 |
| AC-3 | ③ の4分岐がほぼ同時に開始されている | 各分岐先頭ステートの `EnteredTime` の差が1秒未満 |
| AC-4 | **加工A の結果が SQS 到着から10秒以内に DynamoDB にある** | レコードの `elapsedMs < 10000` |
| AC-5 | **加工B/C/D の結果が SQS 到着から15秒以内にある** | レコードの `elapsedMs < 15000` |
| AC-6 | **加工A の書き込みが Parallel 完了より前に起きている** | A の `writtenAt` < Parallel 終了時刻 |
| AC-7 | 実行が `SUCCEEDED` で終わり、DynamoDB に5レコード（加工4＋完了1）ある | `DescribeExecution` + `Query` |
| AC-8 | 同一 `messageId` を再投入しても実行が増えない | `ListExecutions` |

## 9. 前提・制約

- AWS 認証は `aws login` による一時セッション。失効時は再ログインが必要
- IaC は**生の CloudFormation + AWS CLI** のみを使用する（CDK / SAM / Terraform は使わない）
- 検証用途のため、リソースはいつでも `delete-stack` で破棄できる構成にする
- Lambda のコールドスタートにより初回実行は遅くなる。計測は2回目以降も取得して比較する

## 10. 既知の注意点（今回は対象外、追加検証の候補）

- **Parallel は1分岐が失敗すると他の実行中分岐をキャンセルする。** 各分岐に `Catch` を置いて分岐単位で失敗を封じ込める設計が別途必要
- Retry / タイムアウト / Redrive（失敗実行の再開）の挙動
- Express ワークフローとの実行時間・コスト比較
- `Map` + `MaxConcurrency` による同時実行数制御
- X-Ray によるエンドツーエンドのレイテンシ分解
